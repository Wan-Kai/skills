# 开源方案雷达

将用户的目标转化为少量可执行的开源候选，而非罗列搜索结果。用户不需要知道产品名；从业务问题、现用工具或约束开始即可。

## 调研流程

1. 提取目标、关键能力、现有方案和硬约束。硬约束包括部署方式、预算、许可证、语言/地区、数据合规、团队规模、技术栈和上线时间。
2. 判断方案形态：开源产品、自托管服务、AI Skill、MCP Server、Agent 工具，或其组合。目标不明确时，默认同时探索产品与 AI 集成能力，但在结论中明确两者的区别。
3. 按目标选择来源并检索。先读 [references/sources.md](references/sources.md)，只使用与本次任务相关的来源。
4. 为每个进入最终清单的候选核验：官方站点/仓库、许可证、最近发布或提交、维护与 Issue 处理信号、部署路径、关键集成方式及收费依赖。不要把 GitHub Star、Product Hunt 投票或目录收录当作质量结论。
5. 根据用户约束筛掉不合格候选；在相近产品间比较功能覆盖、实施成本、运维成本、迁移难度与锁定风险。
6. 输出推荐结论、备选和下一步验证动作。每个关键事实均附直接来源链接。

## 来源选择

将不同来源视为不同信号，而不是互相替代：

- Product Hunt：发现近期发布、产品化较好的新工具和用户反馈。
- GitHub Trending：发现近期有社区热度的项目；按语言和周期缩小范围。
- GitHub 仓库：核验源码、许可证、更新、Issue、Release 与部署文档，是最终事实来源。
- AlternativeTo / OpenAlternative：从商业产品名称反查开源替代品。
- awesome-selfhosted / 领域 Awesome List：系统发现自托管或垂直领域项目。
- Awesome Agent Skills / skills.sh / 官方 Skill 仓库：发现 Agent Skill、MCP Server 与集成方案。

## GitHub 热榜使用规则

将热榜当作候选发现器，而不是推荐榜。

- 按用户的领域、技术栈和可接受成熟度检索热榜，优先查看同时具备清晰 README、许可证、Release 和可运行示例的仓库。
- 对热榜项目补查维护、部署和社区响应；快速上涨的 Star 不足以说明可生产使用。
- 若用户明确要求“最新”或“本周热门”，单列“新鲜候选”，并与“成熟首选”分开排序。

## 输出格式

先给一句结论，例如“首选 X；若必须私有化部署，选 Y；Z 仅适合快速试用”。随后给出紧凑表格：

| 方案 | 适配原因 | 主要取舍 | 部署/接入 | 证据 |
|---|---|---|---|---|

之后按需要补充：

- **淘汰原因**：只列用户可能会考虑、但被硬约束淘汰的候选。
- **验证清单**：试用前要确认的许可证、身份认证、数据迁移、成本或安全问题。
- **Skill / MCP 搭配**：仅在能显著增强所选产品的使用、开发或运维时提供；不要把它误写成产品本体的替代品。

候选默认给 3–5 个。面对信息不足，先做合理假设并清楚标注；只有会根本改变推荐的问题才向用户追问。

## 质量与安全门槛

- 明确区分“开源核心、开放核心、免费 SaaS、可免费试用”和“可自托管”。
- 引用许可证和安全特性时优先指向官方仓库或官方文档。
- 对需要访问代码、邮箱、数据库、浏览器或生产环境的 Skill/MCP，说明权限范围，建议阅读 `SKILL.md`、安装脚本和依赖后再启用。
- 用户有企业、隐私、合规或生产环境要求时，不推荐来源、维护和授权不清晰的项目作为首选。
